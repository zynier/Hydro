输入、输出、评测边界

A : (M,K)　 B : (N,K)　 C : (M,N)
因为 B 的行向量要和 A 的行向量做点积，所以计算写成 C[i,j] = Σ A[i,k] · B[j,k]，也就是 torch.matmul(A, B.T)。

03 · 萌新版 GPU 体系结构

一条数据要经过哪些地方？

全局显存 HBM

A、B、C 最初都在这里。容量大，但每次访问延迟高。

把整块矩阵反复从 HBM 读，会浪费带宽。

SM / shared memory

一个线程块驻留在一个 SM。shared memory 是 CTA 内可协作的高速暂存。

这里放 6 个 stage，下一段 K 可以提前搬。

Tensor Core / TMEM

Tensor Core 做矩阵乘加。TMEM 是 Blackwell 上给 Tensor Core 用的片上累加空间。

输入 bf16，结果先积在 float。

先记住一个朴素目标：让搬运和计算重叠，让 Tensor Core 少等数据。后面的 T.tma_copy、barrier、双缓冲都在服务这件事。
GPU 不是一块“更快的 CPU”，而是一群能并行工作的 SM

04 · kernel 的三班人马

同一个 256-thread CTA，按线程号分工

线程 0–31 · loader建立 PersistentTileScheduler。每个 K tile 用 TMA 把 A、B 搬进 shared memory，再告诉 loaded barrier “这一段到了”。
线程 32–63 · MMA 发起者等待 loaded，沿 K 维循环调用 tcgen05_gemm。两个 TMEM 槽位轮流接收结果，ko==0 时清零累加器。
线程 128–255 · writer等待 tmem_full，把 TMEM 结果拷到 fragment，再分成 64 列一段写回 C。线程 64–127 在这个版本里不参与主流程。
tx = T.get_thread_binding()
if tx < 32:             # load
elif tx < 64:           # tcgen05 MMA
elif 128 <= tx < 256:  # store
    ...

这里的分支不是三个独立 kernel，而是一个 kernel 内的角色分配。一个 warp 里的 32 个线程通常一起执行同一条指令。

线程分工写得很直白，代价是同步点也变多

05 · TileLang 原语

把 API 当成“GPU 词典”

代码可以先这样理解它解决的麻烦
@jit / @T.prim_func先用 Python 写一个 shape 特化的 kernel 模板把 M、N、K 带进编译期，生成 CUDA/TIR
T.Kernel(...)启动一个持久化 CTA 网格网格大小接近 SM 数，CTA 自己循环领 tile
T.alloc_shared申请 shared memory 数组缓存从 HBM 搬来的 A/B tile
T.tma_copy异步张量搬运搬运可在 Tensor Core 计算时继续进行
T.alloc_tmem申请 Tensor Memory给 tcgen05 MMA 放大块累加结果
T.tcgen05_gemm调用 Blackwell Tensor Core 的矩阵乘加把大量标量乘加换成硬件矩阵指令
T.mbarrier_*带阶段号的生产者/消费者信号保证“数据写完再读，结果读完再复用”

TileLang 的好处在于：这些资源和同步关系在 Python/TIR 层表达，底层模板负责落到具体的 CUDA 指令。

API 名字长，但每个名字都对应一个硬件动作

case 5 的形状

M=113,408
N=128
K=5,120

N 恰好等于一个 128 列 tile。若硬套 2-CTA 路径，合作收益很小，反而多了 cluster 协议。

每个 CTA 负责一个 128×128 的 C tile；K 维有 ceildiv(5120,64)=80 段。Persistent scheduler 让一个 CTA 连续处理很多 M tile。
小 N 的工作形状，常常比“大矩阵通用模板”更值得单独调

07 · 2-CTA cluster 路径

N 较大时，让两个 CTA 一起做一块 256 列的工作

with T.ClusterKernel(
        sm_num, threads=256, cluster_dims=2):
    cta_id = T.block_rank_in_cluster()
    bx = scheduler.m_idx * 2 + cta_id
    by = scheduler.n_idx
    T.tma_copy(
        b[(by * 2 + cta_id) * 128 :
          (by * 2 + cta_id + 1) * 128,
          ko * 64 : (ko + 1) * 64],
        b_shared[phase], barrier=loaded[phase])

    T.tcgen05_gemm(...,
        transpose_B=True, use_2cta=True)

一块 256×256 的结果怎么来

CTA 0A 的 128 行
B 的左半 128 列
+
CTA 1A 的另外 128 行
B 的右半 128 列

cluster barrier 让两个 CTA 能看到彼此约定好的阶段；MMA 指定 use_2cta 后由两 CTA 协同完成 Tensor Core 工作。

写回阶段仍然按 cta_id 选自己的 128 行，避免两个 CTA 把同一片 C 互相覆盖。
cluster 是更大的协作单位，边界也更难写对

08 · 双缓冲 + 多阶段流水线

真正的计算流程：搬第 k+1 段时，算第 k 段

阶段 0TMA 把 A₀/B₀ 放进 shared[0]
阶段 1搬 A₁/B₁，同时 MMA 算 tile₀
阶段 2搬 A₂/B₂，同时 MMA 算 tile₁
阶段 3复用 stage 0 前先等 consumed
阶段 4结果进 TMEM 槽 0/1
阶段 5writer 取结果并写 C

三个 barrier 的方向

  • loaded：shared tile 已经搬完，MMA 可以读
  • consumed：MMA 不再读这个 stage，loader 可以覆盖
  • tmem_full / empty：writer 与下一次 MMA 交换 TMEM 槽

parity 是什么

每个 barrier 有 0/1 两个阶段号。phase // NUM_STAGES 让循环绕回时仍能分辨“这一轮的到达”还是“上一轮的旧信号”。

没有 parity，stage 0 第二次被使用时，线程可能把上一轮的完成信号误当成这一轮的完成信号。
流水线的核心不是“多线程”，而是让不同阶段别互相干等

09 · 关键同步代码

读这几行：它们描述了数据的生命周期

phase = scheduler.current_iter * k_blocks + ko

T.mbarrier_wait_parity(
    consumed[phase % NUM_STAGES],
    ((phase // NUM_STAGES) & 1) ^ 1)

T.tma_copy(a_tile, a_shared[phase % NUM_STAGES],
           barrier=loaded[phase % NUM_STAGES])
T.tma_copy(b_tile, b_shared[phase % NUM_STAGES],
           barrier=loaded[phase % NUM_STAGES])
T.mbarrier_arrive(loaded[phase % NUM_STAGES])

T.mbarrier_wait_parity(loaded[phase % NUM_STAGES],
                        (phase // NUM_STAGES) & 1)
T.tcgen05_gemm(..., mbar=consumed[phase % NUM_STAGES])

1. 等旧读者走开

consumed 防止 loader 覆盖 MMA 还没读完的 shared stage。

2. 发起异步搬运

T.tma_copy 写 shared，完成后到达 loaded。

3. MMA 消费

mbar=consumed 把“我读完了”反馈给 loader。

producer → buffer → consumer → buffer reuse

10 · 入口与 JIT 缓存

提交真正被调用的地方只有十几行

def run_kernel(a, b, c, m, n, k):
    global compiled_shape, real_kernel
    shape = (int(m), int(n), int(k))
    if real_kernel is None:
        compiled_shape = shape
        builder = (matmul_nt_persistent
                   if shape[1] == 128
                   else matmul_nt_persistent_2cta)
        real_kernel = builder(*shape)
    elif shape != compiled_shape:
        raise ValueError(
            f"cached for {compiled_shape}, received {shape}")
    real_kernel(a, b, c)

为什么要缓存

TileLang/JIT 编译会生成和 shape 绑定的 CUDA kernel。评测器把首次编译放在 warmup，所以计时只看后面的 kernel。

这份代码的隐含前提

一个进程里只会跑同一个 shape。这里的全局缓存只有一个槽位；若以后改成同进程混跑多个 shape，需要用字典按 (M,N,K) 缓存。

shape specialization 换来更具体的 tile 和更少的运行时判断

14 · 代码里值得肯定的地方

这份提交为什么能稳定过五个点？

形状分流

N=128 走单 CTA，其余走 2-CTA。它没有逼所有形状共用一套不合身的 tile。

片上复用

A/B 先进入 6-stage shared，K 维循环中反复复用，Tensor Core 读的是片上数据。

异步协作

TMA、mbarrier、TMEM 双槽位把加载、MMA、写回串成一条可重叠的流水线。

数值选择

输入保持 bf16，累加器是 float，最后再写回 bf16，误差能落在评测容差内。

持久化调度

grid 只开到 SM 数附近，CTA 用 scheduler 循环领取 tile，减少超大网格的调度成本。

评测纪律

没有在提交里调用 cudaDeviceSynchronize()，也没有把主要工作丢到计时器看不到的 stream。

从工程角度看，正确性边界、shape 专用化和硬件路径都写得比较清楚。这是“能调优”的 kernel，而不是只靠一个巧合跑快。
成绩背后是几条很具体的工程取舍

15 · 下一轮可以怎么改

先修容易确认的，再碰硬件细节

代码层面

  • 2-CTA writer 里 T.copy(c_shared, c[...]) 出现两次，第二次写入结果相同，应该先确认是否是笔误
  • real_kernel / compiled_shape 只有单槽缓存；多 shape 同进程时改成字典
  • TileLang 警告 scheduler 被重新绑定；按提示用可变变量表达，减少编译器噪声
  • 边界尺寸不是 128/256 的倍数时，确认 TMA 和写回是否有越界保护或 padding 约定

性能层面

  • 用更小的 fragment 或分块写回，减少 register spill 和 local memory
  • 看 shared bank conflict 的具体访问布局，必要时做 padding / swizzle
  • 把 loader 与 writer 的 warp 数做小实验，观察 barrier stall 是否下降
  • 对 case 5 单独调 TMA tile、写回宽度和 CTA 数，不要用前四点的直觉替代测量
不要先把 occupancy 当成唯一目标。这个 kernel 的 TC 利用率已经不低；如果为了多塞几个 warp 而破坏 shared/TMEM 流水线，时间可能反而变长。
优化顺序：先消除确定的冗余，再用 profiler 验证假设
